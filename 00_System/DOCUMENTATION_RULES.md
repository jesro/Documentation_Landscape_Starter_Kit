# Documentation Rules

## Rule 1 — Document knowledge, not activity

Do not create a document merely because a process happened.

## Rule 2 — Match artifact to question

- What are we trying to achieve? -> Context / PRD / Requirements
- What must it do? -> Requirements
- What is the system? -> Architecture
- Why did we choose this? -> ADR
- How will this feature work? -> HLD / LLD
- What did we not know? -> Spike / PoC / Feasibility / Benchmark
- What can go wrong? -> Risk / Threat Model / Debt
- How do we operate it? -> Runbook / Playbook
- What changed? -> Change / Migration / Deprecation
- What happened in discussion? -> Conversation
- What does this term/API mean? -> Reference / Glossary
- What proves governance happened? -> Governance / Compliance
- Why does the product exist? -> Product / Project docs

## Rule 3 — Current state and rationale are different

Architecture docs describe current state.

ADRs preserve rationale.

## Rule 4 — Evidence should point to decisions

Research should be linked from decisions when it materially supports them.

## Rule 5 — Avoid methodology worship

Use the simplest established structure that solves the actual need.
